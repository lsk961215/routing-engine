# 작은 영역 그래프 v1

## 구현 범위

`GraphBuilder`는 기존 자동차 프로필과 회전 제한 검증기를 먼저 실행한다.
보류 도로·회전 제한 검사 사유가 하나라도 있으면 입력을 거부한다. 일반 도로 형상의 모든
OSM Node를 유지하고 연속 좌표 사이에 방향성 간선을 생성한다. 교차점 압축은 하지 않는다.

- 노드: 원본 ID(long), 위도·경도(double, 도).
- 인접 목록: CSR offset(int). 노드 i의 간선은 offset[i] 이상 offset[i+1] 미만.
- 간선: 목적 노드 인덱스(int), 원본 Way ID(long), 구면거리(double, 미터).
- 회전 제한: 금지된 진입·진출 간선 인덱스 쌍(long으로 결합).
- no_*는 해당 도로 조합을 금지하고 only_*는 해당 진입에서 다른 도로로의 진출을 금지한다.
- 같은 from/to Way의 no_u_turn은 원래 노드로 되돌아가는 간선만 금지한다. 그 외 같은 Way 제한은 모호하므로 거부한다.
- Node의 barrier/access 계열은 아직 지원하지 않아 관련 노드가 있으면 거부한다.

속도·예상 시간·공간 인덱스·최단 경로 탐색은 아직 없다. 차량 높이·중량 등 기존 프로필의 미지원 규칙도 남아 있다.
거리 가중치 기반 개발용 그래프이며 운영용 차량 경로 데이터가 아니다.
PBF 8MiB, 노드 10만, 간선 50만, 그래프 파일 64MiB 한도를 둔 작은 영역 전용 구현이다.
`data-builder` 모듈 분리는 후속 작업이며 현재 CLI는 routing-core에 있다.

## 저장 및 적재

`.rgraph`는 big-endian 바이너리이며 magic, 버전(1), 노드·간선·금지 전이 수,
노드 배열, CSR offset, 간선 배열, 금지 전이 배열, CRC32(long 저장) 순서다.
거리 단위와 좌표 형식은 버전 1 규약에 고정한다. 프로필 버전·입력 해시 등 메타데이터 확장은 후속 과제다.

`RoutingGraph.read`는 파일 크기·버전·배열 길이·인덱스·좌표·거리·전이 연결성과 체크섬을 검증한다.
전체를 힙 기본형 배열로 적재하며 생성자에서 복사하고 외부에는 배열을 노출하지 않는다.
파일 버퍼와 배열 복사 때문에 적재 중 최대 메모리는 최종 배열 합보다 크다.
기존 그래프 파일은 자동 덮어쓰지 않는다.

Spring 설정 `routing.graph.path`가 있으면 서버 시작 시 불변 그래프 Bean을 한 번 만든다.
읽기 실패 시 서버 시작이 실패한다. 설정이 없으면 기존처럼 그래프 없이 실행된다.
현재 `/route`는 여전히 hello를 반환하며 이 그래프를 탐색하지 않는다.

## 실제 데이터 검증

보완된 서울 입력에서 bbox `(126.977,37.566) ~ (126.979,37.568)`를 추출했다.
생성 결과: 노드 79개, 방향성 간선 103개, 금지 회전 0개.
해당 입력은 현재 프로필 검사를 통과했다. 이 영역에 회전 제한이 없으므로 제한 변환은 합성 PBF 테스트로 별도 검증했다.

- 파일 크기: 4,304 bytes.
- 배열 본체 합: 4,276 bytes (객체 헤더·임시 버퍼·JVM 제외).
- 단일 재적재 실행: 약 0.419ms. 성능 보장이나 프로세스 메모리 실측은 아니다.
- 그래프 경로를 지정해 서버를 실행하고 `/actuator/health`의 UP 응답 확인. 검증용 서버 종료 완료.
- 백엔드 테스트 25개 통과: PBF 그래프 생성·회전 제한 보존·파일 왕복·손상 및 잘린 파일 거부·잘못된 토폴로지·미해결 제한 거부 포함.

## 재현

프로젝트 루트에서 실행한다. 출력 파일이 이미 있으면 새 경로를 사용한다.

```sh
osmium extract -b 126.977,37.566,126.979,37.568 \
  backend/data/processed/seoul-routing-complete.osm.pbf \
  -o backend/data/processed/graph-small-area.osm.pbf
./backend/gradlew -p backend :routing-core:buildGraph \
  -Ppbf=data/processed/graph-small-area.osm.pbf \
  -Pgraph=data/processed/graph-small-area.rgraph
```

서버 실행 시 `--routing.graph.path=<생성된 그래프의 절대 경로>`를 bootRun의 `--args`에 전달한다.
생성 PBF와 rgraph는 Git에서 제외된다. 작은 합성 PBF 테스트 입력만 저장소에 포함한다.

다음 단계는 이 그래프에서 진입 간선을 상태로 사용하는 Dijkstra를 구현하고,
회전 금지에 따라 우회하거나 경로 없음으로 반환하는 테스트를 만드는 것이다.

## 진입 간선 기반 Dijkstra 구현

`DijkstraRouter`가 거리 기준 최단 경로를 계산한다. 상태는 노드가 아닌 진입 간선 인덱스다.
같은 교차점에 더 긴 거리로 도착하더라도 다른 진입 도로에서 허용되는 회전이 있을 수 있으므로
진입 간선별 최적 거리와 이전 간선을 보관한다. 탐색마다 배열과 우선순위 큐를 새로 만들어 공유 그래프를 변경하지 않는다.

- 입력: 시작·도착 **그래프 노드 인덱스**. OSM ID나 좌표가 아니다.
- 출력: 총 거리(m), 노드·간선 인덱스 순서. 경로가 없으면 Optional.empty / CLI의 NO_ROUTE.
- 출발지에는 이전 진입 간선이 없으므로 출발 간선 자체에 회전 제한을 적용하지 않는다.
- 출발지와 도착지가 같으면 거리 0, 노드 1개, 빈 간선 목록.
- 각 전이에서 `turnAllowed`를 검사한다. 복원된 노드 좌표는 그래프의 latitude/longitude로 조회할 수 있다.
- 요청별 기본 배열은 거리 double + 이전 간선 int로 약 12E bytes. 큐 객체·복원 결과·배열 헤더는 별도다.
- 도로에 좌표 연결, 시간 비용, via-way 제약 상태, API·프론트 연결은 아직 없다.

프로젝트 루트에서 실행:

```sh
./backend/gradlew -p backend :routing-core:routeGraph \
  -Pgraph=data/processed/graph-small-area.rgraph -Pstart=0 -Pend=23
```

실제 작은 영역 결과: 노드 `[0, 71, 5, 23]`, 간선 `[0, 94, 6]`, 거리 약 103.883347m.
0→1은 NO_ROUTE였다. 영역 추출본의 방향성·연결성이 제한되어 모든 노드 쌍에 경로가 있는 것은 아니다.

백엔드 테스트 30개 통과. 새 테스트는 최단 거리·경로 복원, 다른 진입 간선으로 우회,
금지 회전 때문에 경로 없음, 실제 PBF 제한 반영, 파일 재적재 후 탐색, 일방통행,
동일 출발·도착, 잘못된 인덱스, 0비용 순환과 연속 요청 상태 분리를 검증한다.
다음 단계는 좌표와 그래프 연결 방식 정의 및 API 요청·응답 구현이다.

## 좌표 API와 프론트 연동 (초기 버전)

GET `/api/route?startLon=...&startLat=...&endLon=...&endLat=...` (`/route`도 지원).
각 입력에서 50m 이내 가장 가까운 **노드**를 선형 검색하고 Dijkstra를 호출한다.
간선 중간에 투영하는 스냅이 아니므로 평행 도로·교차점·일방통행 인근에서 부정확할 수 있다.
더 먼 노드를 찾아 경로를 억지로 만들지 않는다. 출발·도착이 같은 노드에 연결되면 거리는 0이다.

응답은 `code`, `routes`(GeoJSON geometry, distance, duration=null),
`waypoints`(연결 좌표, 원래 클릭 지점과의 거리)를 포함한다.
거리에는 클릭 지점에서 연결 노드까지의 이동이 포함되지 않는다. 소요 시간·도로명은 아직 제공하지 않는다.
400=잘못된 좌표, 404=경로 없음, 422=50m 안에 노드 없음, 503=그래프 미설정.

프론트는 `/api/route`를 호출한다. Vite 개발 서버는 `/api`를 localhost:8080으로 전달하므로
백엔드를 기본 포트 8080에서 그래프 경로 설정과 함께 실행하고 프론트에서 `npm run dev`를 실행한다.
프로덕션 환경의 동일 출처 API 전달 설정은 별도다.
로딩·오류를 화면에 표시하고 재선택 시 이전 요청을 취소한다.

백엔드 테스트 33개 및 프론트 빌드 통과. 실제 HTTP 요청에서 약 103.883347m, 좌표 4개의
200 응답을 확인했다. 브라우저에서 클릭부터 지도 표시까지의 시각적 검증은 아직 수행하지 않았다.
다음은 간선 구간 투영과 방향을 고려한 좌표 연결, 공간 인덱스 및 브라우저 동작 검증이다.

## 도로 구간 투영과 브라우저 검증 (최신)

이 절은 앞의 최근접 노드 연결 및 브라우저 미검증 상태를 대체한다.
`CoordinateRouter`가 좌표를 50m 이내 가장 가까운 도로 **구간**에 투영한다.

- 서버에서 방향성 간선을 원본 Way ID와 양 끝 노드 쌍 기준으로 묶고, 불변 경계 상자 트리를 한 번 생성한다.
- 조회 시 주변 구간만 찾아 지역 평면 투영으로 연결점을 계산하고, 구면거리로 50m 범위를 확인한다.
- 같은 물리적 구간의 정·역방향 간선을 함께 분할한다. 도로 중간점은 요청별 가상 노드이며 원본 그래프는 변경하지 않는다.
- 구간 길이에 투영 비율을 곱해 부분 거리를 계산한다. 클릭 지점에서 연결점까지의 거리는 경로 거리에 포함하지 않고 waypoint.distance로 반환한다.
- 기존 금지 회전은 원래 진입 간선의 마지막 조각과 진출 간선의 첫 조각으로 옮긴다.
- 가상 노드는 새 교차점이 아니므로 경로 도중 이 지점에서 역방향 간선으로 전환하지 못한다. 출발 시에는 기존 도로에 존재하는 방향 중 선택할 수 있다.
- 좌표가 같더라도 원본 노드·Way가 다른 교차 도로는 연결하지 않는다. 실제 끝점에 붙으면 기존 노드를 사용한다.
- 프론트의 마커도 실제 연결 좌표로 이동한다. 시험 영역을 보기 쉽게 초기 확대 수준을 16으로 조정했다.

현재는 가까운 구간 **한 개**를 선택한다. 여러 평행 도로 후보를 경로 가능성·진행 방향과 함께 평가하는 map matching은 하지 않는다.
지역 평면 투영 방식이므로 작은 도시 영역을 대상으로 하며 날짜변경선을 지나는 구간은 거부한다.
요청마다 분할 그래프와 배열을 복사하므로 전국 규모나 많은 동시 요청에 적합한 최종 구현은 아니다.
공간 인덱스 메모리와 요청별 복제·탐색 메모리를 포함한 최대 RSS 측정도 후속 과제다.

검증 결과:

- 백엔드 테스트 42개 통과. 긴 구간 중간 연결, 부분 거리, 정·역방향, 끝점·동일점,
  금지 회전 우회, 겹치는 비연결 도로, 인덱스 여러 leaf 조회, 동시 요청을 추가 검증했다.
- 프론트 `npm run build` 통과.
- 실제 API: 약 83.658624m 경로, 도로 중간에서 시작·종료하는 좌표 4개 응답.
- Playwright Chromium: 지도 실제 클릭으로 경로선·요약 표시, 재선택 초기화, 일방통행 역방향 404 안내, 영역 밖 422 안내,
  응답 지연 중 재선택 시 이전 결과가 나타나지 않음을 검증했다. 지도 타일을 포함한 스크린샷도 확인했다.

브라우저 재현: backend를 그래프 설정과 함께 8080에서 실행하고 frontend의 `npm run dev`를 실행한 뒤,
Playwright가 설치된 Node 환경에서 `node scripts/browser-route-check.cjs`를 실행한다.
현재 스크립트는 `graph-small-area.rgraph`와 해당 그래프의 예제 간선 0·6에 맞춘 개발용 smoke test다.
테스트 실행 중에만 지도 인스턴스 참조를 주입하며 애플리케이션 소스에는 테스트 전역 변수를 추가하지 않는다.

다음 단계: 지원 영역 확대 전에 프로필·회전 제한의 남은 보류 사례를 처리하고,
메모리 복제 비용을 줄이는 탐색 방식과 규모별 성능을 검증한다.

## 요청당 그래프 복사 제거 (최신 구현)

앞 절의 요청별 분할 그래프 복사 방식은 원본 간선 위의 부분 거리 탐색으로 교체했다.
좌표 연결·일방통행·회전 제한 의미는 유지하며, 출발 초기 비용과 도착 부분 비용만 별도로 계산한다.
설계·동등성 검증·성능 수치는 [ROUTING_PERFORMANCE.md](ROUTING_PERFORMANCE.md)에 정리했다.
