# 서울 데이터 분석 및 메모리 설계 초안

분석일: 2026-09-22. 대상: `processed/seoul-routing.osm.pbf` (44,111,587 bytes).
현재 리더는 원본 통계를 수집하며, 자동차용 그래프를 생성하거나 서버에 적재하지 않는다.
전체 집계는 [seoul-analysis.txt](seoul-analysis.txt)에 기록했다.

후속 자동차 프로필 및 회전 제한 검사(2026-09-23)는 [CAR_PROFILE.md](CAR_PROFILE.md)에 정리했다.
아래 수치는 초기 전체 highway 분석 기준이며, 최신 실행 출력에는 자동차 분석도 포함된다.

## 재현

프로젝트의 `backend` 디렉터리에서 실행한다.

```sh
./gradlew test
./gradlew :routing-core:analyzeOsm
# 다른 입력 파일: backend 기준 상대 경로 또는 절대 경로
./gradlew :routing-core:analyzeOsm -Ppbf=data/processed/seoul-routing.osm.pbf
osmium fileinfo -e data/processed/seoul-routing.osm.pbf
osmium check-refs -r data/processed/seoul-routing.osm.pbf
```

테스트는 저장소에 포함된 합성 PBF를 사용한다. 원본 다운로드와 osmium 설치 없이 실행 가능하다.
합성 데이터의 XML도 테스트 리소스에 함께 보관한다. 변경 시 `osmium cat 입력.osm -o 출력.osm.pbf --overwrite`로 다시 생성한다.

- Node에는 ID와 좌표가 있고 Way는 순서가 있는 노드 ID 목록을 참조한다.
- Relation에는 멤버의 ID·종류·역할과 태그가 있다. 회전 제한은 단순 노드 연결만으로 충분히 표현되지 않는다.
- 노드 ID 최댓값은 14,197,455,650이다. 원본 ID는 `long`, 내부 인덱스는 규모 검증 후 `int`로 분리해야 한다.
- 실제 좌표 범위는 `(126.5829062, 37.1677208) ~ (127.5108660, 37.8849226)`이다. 추출에 지정한 사각형과 실제 포함 노드 범위는 다르다.
- 노드·웨이·관계 수와 좌표 범위를 `osmium fileinfo -e`와 대조해 일치를 확인했다.
- `osmium check-refs -r` 결과 Way가 참조하는 누락 Node는 0이다. Relation의 누락 참조는 Node 1,715, Way 32,069, Relation 489로 보고됐다. 이는 **전체 Relation** 결과이며 회전 제한만의 누락 수는 아직 분리하지 않았다.

## 그래프 설계 전에 해결할 사항

- `highway`에는 `footway` 64,700개, `cycleway` 7,056개, `steps` 5,315개 등도 포함된다. 266,856개를 자동차 도로 수로 해석하면 안 된다.
- `oneway=yes` 32,027개, `oneway=-1` 49개, `oneway=no` 6,559개가 있다. 나머지는 태그 미지정이며 양방향 확정값이 아니다.
- `access`, `vehicle`, `motor_vehicle`, `motorcar` 및 조건부 태그가 존재한다. 자동차 프로필에서 우선순위와 미지정 기본값을 정해야 한다.
- `maxspeed`는 숫자 외에 `15 mph`, 조건부 값도 있다. 원시 값 집계 단계에서는 속도를 임의로 숫자 변환하지 않는다.
- 회전 제한의 `via:Node` 멤버는 5,993개, `via:Way`는 196개다. 이는 관계 수가 아니라 **멤버 수**다.
- 역할명이 빈 Node 5개·Way 7개, 비표준 `via@(8:00-9:00)` 역할 1개가 있다. `from`·`to`·`via`의 누락, 복수 멤버와 참조 존재 여부를 관계별로 검증해야 한다.
- 전체 도로 형상의 중간 노드를 그대로 정점으로 둘지, 교차점 중심으로 압축할지 아직 결정하지 않았다.

## 현재 분석기의 메모리 동작

PBF 엔티티를 순회하면서 카운터와 태그 분포를 모은다. 모든 엔티티 객체를 보관하지는 않지만,
고유 도로 노드 수를 구하기 위해 중복 포함 참조 ID를 확장 가능한 `long[]`에 보관하고 마지막에 정렬한다.
따라서 고정 메모리 스트리밍은 아니며 참조 수에 비례한 메모리가 필요하다.

이번 입력의 ID 버퍼 최종 용량은 2,097,152개, 배열 본체 16MiB다.
확장 도중에는 이전·새 배열이 동시에 존재할 수 있다. PBF 파서와 태그 분포, JVM 비용은 별도다.
단일 배열이므로 매우 큰 입력에는 분할·외부 정렬 등의 대안이 필요하다.

`-Xmx512m`으로 설정한 분석 작업이 성공했고 분석 코드 구간은 약 1.024초였다.
이는 해당 머신의 단일 실행 기록이며, 그래프 적재 성능이나 실제 최대 RSS·힙 사용량 측정값이 아니다.

## 탐색용 메모리 구조 후보

우선 비교 대상으로 기본형 배열 기반 인접 목록(CSR)을 둔다.
노드별 인접 간선 구간은 `offset[node]`부터 `offset[node + 1]` 직전까지로 표현한다.

모든 highway 고유 노드를 유지하고 모든 연속 노드 쌍을 양방향으로 넣는 **가정**이면
N=1,359,438, E=3,051,404다. 실제 차량 프로필·회전 제한 반영 후 수치는 달라진다.

| 구성 | 배열 본체 계산 | 예상 크기 |
| --- | --- | ---: |
| 노드 좌표 | int 위도·경도 2개 × N | 10.37MiB |
| 노드별 간선 시작점 | int × (N+1) | 5.19MiB |
| 방향성 간선 목적지·거리·시간 | int 3개 × E | 34.92MiB |
| 위 3개 합계 | 12N + 4 + 12E bytes | 50.48MiB |
| 원본 ID 배열 (별도) | long × N | 10.37MiB |
| 요청별 비용·이전 노드·방문 상태 예시 | double + int + byte × N | 16.85MiB/요청 |

이는 서버 전체 메모리 예산이 아니다. 공간 인덱스, 도로명·형상 연결, 회전 제한,
원본 ID 검색 구조, 우선순위 큐, 배열 헤더, 런타임·프레임워크와 가공 중 임시 데이터가 빠져 있다.
요청별 16.85MiB 예시 역시 회전 제한에 따른 간선 기반 탐색 상태와 큐 비용을 포함하지 않는다.
좌표 스케일과 거리·시간 단위, 오버플로 처리도 설계 단계에서 확정해야 한다.

## 권장 적재 흐름과 다음 작업

1. 자동차 프로필과 회전 제한 검증 규칙을 정하고 실제 유지할 노드·간선을 집계한다.
2. 오프라인 가공 단계에서 원본 ID를 연속 인덱스로 변환하고 그래프·형상·제한을 생성한다.
3. 버전·개수·단위·무결성 정보를 갖는 가공 파일 형식을 정의한다.
4. 서버 시작 시 파일을 검증하고 읽기 전용 공통 그래프를 한 번 적재한다. 준비 완료 전 탐색 요청은 받지 않는다.
5. 요청별 탐색 작업 공간은 공통 그래프와 분리하고 동시 요청 수를 제한해 메모리 상한을 관리한다.
6. 실제 적재·탐색 메모리를 측정한 뒤 힙 배열과 파일 매핑 중 방식을 확정한다.

현재 단계에서는 파일 매핑이나 전국 데이터 적재 방식을 확정하지 않는다.

## 코드 리뷰 반영

- 로컬 대용량 파일에 의존하며 출력만 하던 테스트를 합성 데이터 기반 assertion 테스트로 교체했다.
- 입력 파일이 없을 때는 `Files.newInputStream`의 `NoSuchFileException`으로 실패한다.
- 중복 참조, 32비트보다 큰 원본 ID, 단방향 태그, 차량별·조건부 태그, via-way 제한, 노드 없는 입력을 검증한다.
- 결과의 중첩 맵은 정렬된 읽기 전용 복사본으로 반환한다.
- 분석 CLI를 테스트와 분리했다. 입력 손상·잘린 PBF 전체를 검증하는 기능은 아직 없으며, 운영 로더 도입 전에 보완해야 한다.
